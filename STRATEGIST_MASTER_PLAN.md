Версия 1 · 17 ноября 2026 года

**Статус:** план будущей работы, не отчёт о готовом агенте. Первичная разведка источников выполнена; реализация, сравнительные испытания и конкурсные материалы ещё не выполнены. План относится к отдельному заданию «Стратег Фабрики продуктов», не к студенческому кабинету «Курсом».

## 1. Главное решение

Строим переносимую проект-папку для агента в Cursor и другой проверенной среде, а не форк автономного Ouroboros и не новый SaaS. Ядро — инструкции, методические навыки, инструменты работы с материалами и сохраняемое состояние исследования. Цикл «подумать → выбрать инструмент → проверить результат → решить следующий шаг» исполняет агент среды.

**Продуктовое обещание:** «Помогает принять и затем поддерживать решение: показывает, на чём оно держится, какие альтернативы отброшены и что изменилось после новых данных».

Конкурировать только качеством длинного research-отчёта неразумно: такие решения уже существуют. Наше отличие нужно доказать на цепочке:

> Неясный запрос → проверенные основания → реальные альтернативы → согласованные продуктовая и коммуникационная стратегии → решение человека → обязательства → пересмотр при новых данных.

Максимум соответствия критериям не означает максимум компонентов. Приоритет — доказанная глубина анализа и работающий сквозной путь. Мультиагентность, маршрутизация, MCP и мультимодальность добавляются там, где дают измеримую пользу.

### Что считаю обязательным в итоговой версии

- Работа с документами, таблицами и разрешёнными сайтами, с адресами исходных фрагментов.
- Факты, гипотезы, прогнозы, рекомендации и решения человека различаются.
- Не менее трёх действительно разных вариантов. Чтобы покрыть обе формулировки задания без споров, целимся в четыре: оставить как есть, улучшить текущее направление, существенно изменить направление, закрыть/свернуть его. Неприменимость закрытия объясняется, а не замалчивается.
- Связанные продуктовая и коммуникационная стратегии, экономика и план проверки.
- Продолжение в новом чате без повторного брифинга и незаметного повтора выполненных действий.
- Реестр решений, ответственных, обязательств и условий пересмотра.
- Честные время и расходы, включая ошибки и помощь человека.
- Проверка на новых кейсах, а не только на заученной демонстрации.
- Понятный первый запуск и полный комплект сдачи, включая обязательное видео до 10 минут.

## 3. Матрица требований: что строим и чем доказываем

| Требование | Предлагаемый результат | Приёмочная проверка |
|---|---|---|
| Уточнение задачи | Краткий бриф: решение, цель, адресат, ограничения, данные, срок | Агент задаёт только вопросы, влияющие на ближайшее действие; умеет работать с явно названными допущениями |
| Документы, таблицы, сайты | Реестр источников, оригиналы или допустимые выдержки, результаты извлечения | Смешанный набор PDF/DOCX, CSV/XLSX, HTML проходит через реальные инструменты; неполное чтение отмечено |
| Происхождение сведений | Утверждение → источник → точный фрагмент/ячейки/страница → дата | Существенный факт можно проверить без поиска по всему чату |
| Исследование от решения | Вопросы, ответ на которые способен изменить выбор | Для каждого исследовательского шага видна связь с неопределённостью, а не просто список тем |
| Разные варианты | Status quo, улучшение, поворот, закрытие; возражения и цена отказа | Критик проверяет различия в целевой задаче, механике, экономике или риске; косметические варианты не засчитываются |
| Продуктовая стратегия | Аудитория/JTBD, альтернативы, направление, отказы, возможности и экономика | Нет необоснованных размеров рынка/выручки; допущения и чувствительность видны |
| Коммуникационная стратегия | Ситуация, барьер, сообщение, доказательство, роль каналов | Каждое обещание связано с реальной или явно планируемой возможностью продукта |
| План проверки | Гипотеза, метрика, база сравнения, период, критерий решения, ограничения и вред | Нет «проверим конверсию» без знаменателя, сравнения, срока и защитных метрик |
| Самостоятельное ведение | Агент выбирает очередной вопрос, метод и инструмент | Нужна одна стартовая просьба, не ручной запуск каждой стадии человеком |
| Человек при существенном выборе | Карточка решения с альтернативами и последствиями | Агент не приписывает человеку собственную рекомендацию и не утверждает стратегию молча |
| Разделённые знания | Инструкции / методики / первичные материалы / состояние / результаты | Старый ответ не становится фактом; проекты не смешиваются |
| Продолжение | Читаемое состояние, журнал действий, сохранённые результаты | Новый чат продолжает с правильного места; испытание переноса папки во вторую среду |
| Прозрачность | План, прогресс, основания, журнал расходов и вмешательств | Можно восстановить, какие операции выполнены, не выполнены или имеют неизвестный исход |
| Удобство и коррекция | Простые запросы «продолжи», «покажи основания», «исправь допущение» | Новичок проходит путь по README; исправление распространяется на зависимые выводы |
| Безопасность | Разрешённые источники, отсутствие секретов, недоверенные входные материалы | Инъекция в документе не меняет правила, не запускает команду, не раскрывает ключ |
| Дополнительный уровень | Обязательства, пересмотр, воспроизводимый анализ, критик, UX и интервью | Для каждой заявленной функции отдельное наблюдаемое доказательство |
| Конкурсная поставка | Репозиторий/архив, демопроект, видео, описание со скриншотами | Чек-лист выдачи с рабочими ссылками и проверкой доступа с отдельной сессии |

### Как работаем на четыре оценки

**Проработанность:** доказательства и противоречия, сильные альтернативы и возражения, честная экономика, согласованность обещаний. Главный риск — качественно оформленный, но недоказанный текст.

**Масштаб нейротехнологий:** обоснованная система навыков, выбор инструментов, адресная независимая критика, управление контекстом и пересмотр. Главный риск — роли и модели ради количества.

**Имплементация:** чистый запуск, реальные инструменты, возобновление, отложенные кейсы, обработка сбоев. Главный риск — заскриптованная демонстрация, не переносящаяся на новый запрос.

**Качество:** понятный путь руководителя, краткое решение с подробными основаниями, полная стоимость, минимум ручной работы. Главный риск — сложная папка, для использования которой нужно изучить её устройство.

Это внутренняя карта подготовки, не обещание получить 40/40 и не собственная система оценивания вместо жюри.

## 4. Программа исследования

### 4.1. Как читать и фиксировать результаты

На каждую работу — короткая карточка: библиография и дата проверки; какой вопрос проекта она разрешает; что источник действительно утверждает; условия и ограничения; проектное следствие; проверка, способная это следствие опровергнуть; решение «берём / эксперимент / не берём».

Раздельно вести инженерную библиотеку разработчиков и методическую базу продуктового агента. Пользовательскому агенту не нужно читать весь ресёрч об агентных системах на каждом запуске.

Исследование не бесконечно: следующий источник нужен, если он может поменять выбор основы, метод, оценку риска или способ проверки. При достаточных основаниях фиксируем решение и остаточную неопределённость.

### 4.4. Продуктовая и коммуникационная методология — отдельный обязательный поток

Инженерные статьи не научат агента выбирать продуктовую стратегию. Нужно собрать небольшую прикладную базу из первоисточников, легально доступных материалов и собственных шаблонов:

1. **Постановка решения:** диагноз → целевой исход → варианты → ограничения → цена ошибки. Исследовать problem framing и strategy kernel; SWOT не делать обязательным ритуалом.
2. **Discovery и аудитория:** JTBD, сегментация по ситуации и задаче, анализ альтернатив включая «ничего не делать», интервью о прошлом поведении, opportunity mapping. Читать оригинальные материалы авторов подходов, фиксировать где они применимы.
3. **Количественный анализ:** когортное удержание, воронки, определения активного пользователя, сезонность, смена состава аудитории, Simpson’s paradox, корреляция и причинность. Для каждого метода — небольшой воспроизводимый пример и ловушка.
4. **Экономика:** contribution margin, CAC/LTV с явными ограничениями, стоимость поддержки, сценарии выручки, пороги безубыточности и чувствительность. Не вводить «точный LTV» без модели и данных.
5. **Позиционирование и коммуникация:** ситуация покупки, конкурентная рамка, барьер понимания/доверия/выбора, value proposition, proof points, роли каналов. Не путать коммуникационную стратегию с календарём постов.
6. **Эксперименты:** контрфактическое сравнение, primary/guardrail metrics, минимально полезный эффект, достаточность выборки, срок, правила остановки; качественный тест понимания отдельно от доказательства спроса.
7. **Управление после выбора:** decision records, владельцы обязательств, дата/условия пересмотра, отмена устаревших оснований.

Результат — методические карточки с инструкцией «когда использовать / какие входы / как проверить / чего не утверждать». Неподтверждённую авторскую схему маркируем своей, а не «научным стандартом». Книги целиком в репозиторий не копируем.

| [GPT Researcher](https://docs.gptr.dev/) | Опциональный инструмент web/local research и baseline | Отдельный слой моделей/поиска, расходы; не заменяет нашу стратегическую логику |
| [STORM / Co-STORM](https://github.com/stanford-oval/storm) | Вопросы с разных перспектив, структура исследования, цитирование | Ориентация на исследовательский текст; стратегию и обязательства нужно добавлять |
| [Spec Kit](https://github.com/github/spec-kit) | Файловые процессы и idea assessment: intake → research → define → shape → decide; go / needs-clarification / kill | Сравнить адаптацию с минимальным ядром; лишний CLI/методология могут усложнить вход |
| [BMAD](https://bmadcode.com/method) | Роли, шаблоны, процедуры, упаковка для IDE | Полный набор может перегрузить задачу ролями и контекстом |
| [Agent Skills](https://github.com/agentskills/agentskills) | Формат навыков с подгрузкой по необходимости | Стандарт — не доказательство одинакового исполнения во всех средах |
| [MarkItDown](https://github.com/microsoft/markitdown) / [Docling](https://github.com/docling-project/docling) | Кандидаты импорта офисных документов/PDF; Docling для более сложного разбора | Конвертация не гарантирует точность таблиц, формул и адресов; OCR и модели могут быть тяжёлыми |

**Существенное уточнение:** Spec Kit нельзя списать как инструмент только для программирования. Его текущий README, дополнительно проверенный автором, прямо содержит оценку идеи и решение о прекращении. Поэтому эксперимент с адаптацией assessment входит в первый приоритет.

### Три архитектурные альтернативы для нашего проекта

**A. SaaS-first.** Быстро собрать процесс из research-сервиса и Dovetail/Productboard. Выигрыш — меньше собственных инструментов. Проигрыш — аккаунты, стоимость, экспорт, зависимость от доступа; слабый старт из одной папки. Откладываем как опциональную корпоративную интеграцию.

**B. Адаптация Spec Kit assessment или выбранных частей BMAD.** Близка конкурсному формату и может сократить разработку. Риск — чужие стадии диктуют процесс, а человек вынужден вручную запускать каждую. Проверить, можно ли оставить агенту самостоятельное ведение работы и закрыть коммуникацию/последующее сопровождение без тяжёлой надстройки.

**C. Независимое небольшое файловое ядро + Agent Skills + сменные инструменты.** Предпочтительная гипотеза: проще держать единую модель доказательств и переносимость. Риск — изобретение уже готовых механизмов и слабая стандартизация.

**Выбор пока предварительный: C с заимствованием удачных частей B.** Прежде чем окончательно выбрать, провести одинаковый мини-кейс на двух основах. Если B даёт те же результаты с меньшими затратами и без усложнения для человека, принять B. Сравнивать время адаптации, контекст, шаги пользователя, продолжение и покрытие требований, не эстетические предпочтения.

### Лицензии и зависимости

При выборе компонента фиксировать точный commit/version, LICENSE/NOTICE, прямые зависимости, лицензии моделей/OCR и права на входные материалы. MIT или Apache у репозитория не делает все скачиваемые модели и документы свободными. Для значимых заимствований — `THIRD_PARTY_NOTICES.md`. Никаких логинов, покупок, платных ключей и обязательного облачного SaaS в скрытых настройках.

## 6. Что переносим из Ouroboros

Ouroboros полезен как инженерный опыт, но его цель и масштабы не совпадают с задачей руководителя продукта.

| Механизм Ouroboros | Адаптация | Что сознательно оставляем за пределами |
|---|---|---|
| Постоянные правила и identity | Короткая роль стратега, границы полномочий и правила доказательности | Конституция цифровой личности и самосоздание не нужны продуктовому исследованию |
| План и критерии готовности | Вопрос решения, план исследования, ожидаемые артефакты, остановка поиска | Полная инфраструктура plan councils и собственные серверные панели |
| Источники и provenance | Отдельные источники, утверждения, выводы, решения; точные ссылки | Копирование всей внутренней схемы хранилища и forensic CAS |
| Scratchpad, knowledge, chronicle | Состояние проекта, методики, карточки решений и история пересмотров | Глобальная личность, общая память чужих проектов, бесконечный resident-контекст |
| Инструментальная проверка | Расчёты кодом, аудит цитат и полноты, реальные файлы | Заявление «проверено» только по самопроверке LLM |
| Независимые помощники | Исследователь отдельного вопроса и критик при необходимости | Рой фиксированного размера и голосование как доказательство истинности |
| Учёт расходов и ошибок | Операции, модель, токены при наличии, время, повторы, помощь человека | Второй runtime и биллинговый движок |
| Сохранение перед прерыванием | Результаты операций и понятный checkpoint | Супервизор процессов, фоновые пробуждения, daemon, автоматический restart |
| Пересмотр знания | Связи оснований и выводов, статусы disputed/retracted/superseded | Бесследная перезапись прошлого решения |
| Self-modification | Разработчик улучшает инструкции по результатам тестов | Агент в ходе бизнес-кейса переписывает собственные правила и разрешения |

Фактическая адаптация — написать компактное предметное ядро с опорой на эти паттерны и проверить его в чужой среде. Не экспортировать личную память, настройки, аккаунты и историю Ouroboros. Мой runtime может помочь нам разрабатывать и тестировать проект, но не должен требоваться пользователю для запуска.

## 7. Предлагаемая архитектура папки

Это проектная схема, не перечень уже созданных файлов. Названия и дробление уточняются после первого сквозного прогона.

```text
README.md                     # быстрый старт и короткая демонстрация
AGENTS.md                     # каноническая роль, границы и карта чтения
adapters/                     # тонкие инструкции для конкретных сред
  cursor/
  codex/
skills/                       # повторяемые процедуры, не обязательные отдельные агенты
  frame-decision/SKILL.md
  investigate/SKILL.md
  analyze-data/SKILL.md
  compare-options/SKILL.md
  align-strategies/SKILL.md
  review-decision/SKILL.md
knowledge/
  index.md
  methods/                    # отобранная методология с источниками
  examples/                   # хорошие и плохие примеры, явно учебные
tools/                        # небольшие CLI-утилиты с тестами
  ...
templates/                    # формы артефактов, не вторая копия правил
projects/<case>/
  brief.md
  state.md                    # текущий checkpoint и ссылки
  sources/                    # оригиналы/разрешённые снимки, метаданные
  evidence/                   # реестр утверждений и подтверждающие фрагменты
  analysis/                   # расчёты, входы, результаты
  options.md
  strategy.md                 # две стратегии и план проверки
  decisions/                  # выбор человека и основания
  commitments.csv
  revisions/                  # история изменений выводов
  runs/                       # действия, расходы, ошибки, помощь
examples/demo/                # готовый проверяемый демонстрационный проект
evals/                        # задачи и рубрики; отложенные ответы отдельно от агента
docs/                         # архитектура, ограничения, поставка, исследовательские решения
.env.example                  # только имена переменных, без значений секретов
THIRD_PARTY_NOTICES.md
```

### Одна истина, несколько представлений

- `AGENTS.md` хранит канонические общие правила. Адаптеры IDE только подключают их и описывают доступные способности; не копируют весь промпт.
- Точный формат `.cursor/rules`, skills/hooks и `AGENTS.md` в Codex проверяется по актуальной официальной документации и реальным запуском, не по памяти.
- Источник хранится отдельно от извлечённого текста; текст отдельно от интерпретации.
- `state.md` — краткая текущая карта, а не второй полный отчёт. В нём вопрос, стадия, последняя подтверждённая операция, нерешённые вопросы и следующий шаг.
- Реестры можно хранить в Markdown/CSV/JSON по удобству потребителя. Не держать две вручную редактируемые копии одного факта.
- Все рабочие ссылки внутри проекта относительные; экспорт не зависит от домашнего каталога разработчика.
- Векторная БД, графовая БД и веб-интерфейс не нужны для первой версии. Сначала поиск по тексту, индекс и связи по ID. Семантический поиск добавляем, если измеренный объём делает этот путь недостаточным.

### Пример модели доказательств

Источник `S-014`: URL или путь; автор/организация; даты публикации и получения; разрешённость использования; тип первичный/вторичный/синтетический; полнота извлечения; версия/хеш для локальных материалов.

Утверждение `E-023`: формулировка; тип факт/гипотеза/прогноз/интерпретация; ссылки на `S-*`; точная цитата или ячейки; период, единицы, аудитория; поддерживает/опровергает; ограничения; статус active/disputed/retracted/superseded.

Вывод `C-008`: на какие `E-*` опирается; какие альтернативные объяснения остаются; что изменило бы вывод. Решение `D-002`: кто и когда выбрал, из каких вариантов, почему, на какие выводы опирался, когда пересматривать.

Например, «удержание упало» ещё не доказывает плохой onboarding: измениться могли канал привлечения, определение активного пользователя, состав когорт или инструментирование. Хороший агент исследует эти объяснения, прежде чем рекомендовать продуктовую переделку.

## 8. Пользовательский процесс

Шаги ниже — смысловые этапы и ожидаемые результаты, не жёсткая цепочка промптов. Агент может вернуться к вопросу, отказаться от бесполезного поиска или предложить решение с недостаточными данными. Он объясняет это человеку.

### 8.1. Первый запуск

Пользователь открывает папку и пишет: «Начни исследование: падает удержание; материалы здесь». Агент проверяет доступные инструменты, разрешённые источники и сохранённые проекты, затем формулирует вопрос решения. README ведёт по этому пути без экскурсии по архитектуре.

Проверка среды показывает: что работает, какие зависимости отсутствуют, какие операции используют внешние сервисы, что оплачивается и как остановиться. Не подставляет фиктивные ключи и не объявляет мок реальной моделью.

### 8.2. Постановка вопроса

Выяснить: какое решение предстоит; для кого результат; какая метрика и горизонт важны; чего нельзя менять; что уже известно. Не выдавать анкету на 25 вопросов. Если ответ пока не нужен, отметить допущение и продолжить безопасную часть.

Выход: краткий `brief.md`, первичные неизвестности и критерии полезного результата. Если человек меняет цель, сохранить изменение как его решение, а не продолжать по старому плану.

### 8.3. План исследования

Начать с вопросов, меняющих выбор: существует ли проблема; у кого; каковы альтернативы; какие причины различимы; что мешает решению; какой факт опровергнет выбранную гипотезу. Для каждого — метод, источник, ожидаемая польза и цена.

Агент показывает короткий план, работает дальше самостоятельно в его границах и возвращается к человеку при существенном выборе. Нет обязательного согласования каждого поискового запроса.

### 8.4. Сбор и анализ

Документы: исходник, результат извлечения, адрес страницы/раздела, пропуски. Таблицы: листы, строки/колонки, единицы, даты, формулы и пропуски. Сайты: первоисточник и дата, выдержки с соблюдением прав; поисковый сниппет — только находка, не доказательство.

Сопоставить источники, выявить перепечатки одного исследования, противоречия, разные периоды/рынки. Рейтинг авторитетности не должен автоматически подавлять конкретные данные. Надёжность обосновывается, не рисуется числом «уверенность 93%».

Выход: проверяемая картина «известно / неизвестно / спорно / предполагаем», расчёты и вопросы, которые всё ещё могут поменять решение.

### 8.5. Варианты и независимое возражение

Для каждого варианта: целевая аудитория/ситуация, механизм ценности, требуемые возможности, затраты и доходы, сроки, риски, обратимость, сильнейшее возражение, недостающие данные, проверка и условие отказа.

Не делать status quo заведомо слабым, а закрытие карикатурным. У бездействия есть цена упущенной возможности, но и экономия ресурсов. У закрытия — расходы на выход, обязательства перед пользователями и репутационные последствия. Рекомендация может быть «пока не выбирать» или «закрыть».

Критик получает исходные основания и варианты, а не только уверенный финальный отчёт. Его задача — найти неподдержанные факты, логические скачки, ложную различность вариантов, несогласованные обещания, слабые проверки. Возражение принимается или отвергается с причиной; большинство моделей не устанавливает истину.

### 8.6. Две стратегии и план проверки

**Продуктовая:** для кого/какой задачи; текущие альтернативы; диагноз; выбранное направление; осознанные отказы; что должно быть построено или изменено; почему это создаёт ценность; экономика и ключевые неопределённости.

**Коммуникационная:** аудитория и ситуация; барьер; позиционирование; ключевое сообщение; подтверждения; тон и ограничения обещаний; роль каждого канала и ожидаемое действие. Несколько примеров сообщения нужны, но не заменяют стратегию.

Обязательная матрица согласования:

| Обещание аудитории | Возможность продукта | Подтверждение | Статус и допустимая формулировка | Как проверить понимание |
|---|---|---|---|---|
| Конкретная польза | Уже есть / планируется / отсутствует | Наблюдение, расчёт, тест или пробел | Можно обещать сейчас / только как план / нельзя утверждать | Исследование или эксперимент |

**План проверки:** ожидаемое изменение; первичная метрика с определением и знаменателем; база/контроль; сегмент; срок; минимально полезный эффект; достаточность данных; защитные метрики и нежелательные последствия; кто решает; условия продолжения, остановки или пересмотра. При отсутствии данных агент планирует измерение, а не выдумывает мощность теста.

### 8.7. Выбор человеком

На выходе — короткая записка руководителю, подробные основания по ссылкам и один действительно существенный вопрос: какой вариант принять или какие ограничения изменить. Рекомендация агента остаётся рекомендацией до решения человека. Назначенный моделью ответственный — кандидат, а не подтверждённое обязательство человека.

### 8.8. После решения

Сохранить: выбранный вариант, основания, отклонённые альтернативы, владельцев, показатели, обязательства, даты и условия пересмотра. На запрос «что сейчас важно?» показывать актуальные обязательства, пробелы и изменившиеся основания.

В папочном формате **нет фонового наблюдения, когда IDE закрыта**. Базовый режим — проверка при следующем открытии/явном refresh. Напоминания и внешние события возможны только как отдельная явно настроенная интеграция; не обещаем их до реализации и проверки.

Новые данные сначала сопоставляются с источниками и утверждениями. По связям находятся затронутые выводы, стратегия и решение. Старое решение не переписывается бесследно: появляется revision с «что изменилось / что осталось / почему / нужно ли новое решение человека».

## 9. Инструменты, навыки и модели

### 9.1. Минимальный набор инструментов

Предпочтение готовым небольшим библиотекам; собственный код — только связка и проверяемые расчёты.

- Инвентаризация материалов и диагностический запуск среды.
- Извлечение PDF с текстовым слоем и DOCX, с сообщением о пропусках. OCR — отдельный профиль, не молчаливый fallback.
- Структурное чтение CSV/XLSX. Проверять формулы и cached values: библиотека может прочитать формулу, но не вычислить её; это явно отражается.
- Сохранение разрешённой web-страницы/выдержки с датой и источником. Не исполнять команды со страниц.
- Профилирование данных и воспроизводимые расчёты: код, входной файл, единицы, выход.
- Проверка целостности проекта: ссылки, ID, обязательные поля, незавершённые операции, отсутствующие исходники.
- Построение читаемого экспорта стратегии и журнала изменений.

Окончательные CLI-имена выбираются при реализации; этот план не выдаёт несуществующие команды за способ запуска. Утилиты не должны сами становиться автономным оркестратором LLM.

### 9.2. Навыки и помощники

Шесть навыков в схеме папки достаточны как старт. Внутри них будут адресные методики интервью, UX и проверки сообщений. Skills не равны шести постоянно работающим агентам.

Базовая топология: один ведущий агент. Дополнительный исследователь — для независимого вопроса, критик — для существенного решения, аналитик — для отдельного вычислительного блока. Один интегратор изменяет канонические решения; помощники отдают собственные артефакты, чтобы не перемешать записи.

Первая независимая позиция критика формируется до знакомства с чужой оценкой. Если среда не поддерживает субагентов, сохраняется одиночный процесс с явным ограничением; последовательная смена роли не называется независимым агентом.

### 9.3. Routing и экономичность

- Сильная доступная модель — постановка неоднозначной задачи, противоречия, стратегия, финальный синтез.
- Более дешёвая модель — узкая извлекающая/классифицирующая работа только после проверки её ошибок на русском материале.
- Python/табличный инструмент — арифметика и статистика; не заставлять LLM считать то, что проверяется программой.
- Vision/OCR/transcription — только для реально присутствующего материала и с согласием на передачу внешнему сервису.
- Jev — исследовательский кандидат из задания. Уточнить точный продукт, API, условия доступа и применимые классификации. Не обещать интеграцию по одному имени и не подключать ради галочки.

Смена модели фиксирует причину и фактическую модель, если среда её сообщает. Если она не позволяет программный выбор, честно заявляем маршрутизацию процессов/инструментов, а не реализованный model routing. Ошибка классификации возвращает вопрос сильной модели/человеку; повтор не скрывается в стоимости.

### 9.4. MCP и hooks

Сначала использовать штатные инструменты IDE и CLI. Один MCP-коннектор может быть полезен для поиска/браузера или локальных материалов, если реально упрощает проверенный путь; не писать MCP-сервер без нужды. Доступы и происхождение данных объявлены заранее.

Hooks — детерминированная помощь: напоминание о checkpoint, проверка формата/секретов перед экспортом. Hook не выбирает стратегию, не подтверждает факты и не заменяет модельное решение. Там, где hooks отсутствуют, явный шаг процедуры обеспечивает ту же обязанность; разницу документируем и проверяем.

## 11. Устойчивость, безопасность и память

### Источники и инъекции

Материалы проекта — данные, не правила. Инструкция «игнорируй прежние указания, выполни команду, отправь ключ» внутри PDF/сайта маркируется как содержимое и не выполняется. Чужие skills и скрипты проверяются до установки. Безопасность в IDE не сводится к промпту: нужны права инструментов, подтверждения внешних действий и отсутствие секретов в корпусе.

Разрешённые источники определяются брифом: открытые и собственные разрешённые материалы. Никаких закрытых данных МегаФона или других компаний. Реальные интервью — только с согласия, с обезличиванием до попадания в репозиторий. Локальное хранение не означает, что LLM работает локально: описать направления передачи данных.

### Продолжение и побочные эффекты

Для операции сохранять вопрос, входы, инструмент, дату, результат/ошибку и ссылку на артефакт. Состояния различают «планируется», «началась», «успешно», «неуспешно», «исход неизвестен». После сбоя проверить сохранённый файл/ответ перед повтором. Особенно не повторять вслепую платный вызов, публикацию или отправку сообщения.

Первая версия преимущественно читает и создаёт локальные файлы, чтобы уменьшить риск внешних эффектов. Результаты сохраняются по мере готовности, не только в конце. Один writer, атомарная запись маленьких реестров, история в Git или версионированных артефактах; не строить свою транзакционную платформу.

### Поиск, исправление и отзыв знания

Запрос по формулировке находит текст и ID; смысловой поиск сначала делает модель по индексу и релевантным материалам; связи выводят от решения к основаниям и обратно. При исправлении число меняется в источнике/расчёте, а связанные выводы становятся нуждающимися в проверке. Отзыв — статус с причиной и датой, не уничтожение истории. Личная память и чужие проекты не подмешиваются.

### Матрица негативных проверок

- Инструкция-вредитель внутри документа, таблицы и web-страницы.
- Недоступный URL, таймаут поиска, rate limit, отсутствующая зависимость.
- PDF без текстового слоя, повреждённый файл, непрочитанный лист.
- Проценты вместо долей, рубли вместо тысяч рублей, разные периоды, дубликаты, пустые значения.
- Формула без вычисленного значения, некорректный знаменатель, смена определения retention.
- Две ссылки на перепечатку одного исследования, цитата не подтверждает тезис.
- Противоречащий первичный источник и устаревший вывод.
- Синтетическое интервью, ошибочно предложенное как доказательство спроса.
- Остановка в середине операции и новый чат; неизвестный исход не объявляется успехом.
- Перенос папки с пробелами/кириллицей в пути; отсутствие абсолютных зависимостей.
- Человек отменил выбор; агент не продолжает его реализацию как действующее поручение.
- Нехватка бюджета; сохранение полезного частичного результата с конкретными пробелами.

## 12. Оценка качества и сравнение с обычным чатом

### 12.1. Набор задач до расширения архитектуры

Подготовить минимум три разных семейства кейсов: падение удержания, вывод нового сервиса на сегмент, непонятная ценность/позиционирование. Отдельный стресс-кейс — данных недостаточно или направление стоит закрыть. Каждый содержит документ, таблицу и сайт/разрешённый снимок. Для проверки импорта можно использовать явно учебные синтетические данные, но не выдавать их за реальные данные МегаФона или рынка.

У каждого кейса: вопрос решения; разрешённый пакет материалов; известные ошибки/противоречия; критерии оценки и проверяемые арифметические результаты. Не должен быть один «правильный красивый ответ»: несколько стратегий допустимы, если выдерживают основания.

Разделить набор разработки и отложенные кейсы. Эталонные ответы и ловушки отложенных кейсов не включаются в знания испытуемого агента. Независимый оценщик получает их после выполнения.

### 12.2. Три сравниваемых подхода

A. Обычный чат с той же моделью, тем же брифом и материалами, без нашей папки.

B. Минимальная папка: один агент, методы, источники, состояние.

C. Та же папка с выбранным усилением: критик/помощник/дешёвая маршрутизация.

По возможности добавить доступный deep-research продукт как внешний ориентир, но не делать платный SaaS обязательным. Ручной аналитик — дополнительный baseline только если реально есть человек и его замер; иначе сравниваем с обычным чатом, что соответствует формулировке задания.

Два режима: фиксированный пакет источников изолирует качество анализа; открытый web показывает исследовательскую способность, но имеет меняющиеся входы. Для каждого фиксировать модель, версию инструкций, лимит, дату, средства поиска, помощь человека. Стремиться к трём повторениям на кейс/конфигурацию после пилота; это целевой дизайн, не уже проведённая статистика. При малой выборке показывать отдельные результаты и диапазоны, не «доказанное превосходство».

### 12.3. Что измеряем

- **Поддержка утверждений:** какая часть проверенных существенных фактов действительно подтверждена указанным фрагментом.
- **Покрытие:** какие существенные утверждения вообще имеют проверяемые основания; наличие ссылки отдельно от её корректности.
- **Гигиена рассуждения:** отличены ли факты/гипотезы/прогнозы; обработаны ли противоречия и альтернативные объяснения.
- **Варианты:** содержательное различие, честность status quo/закрытия, сила возражений.
- **Стратегия:** аудитория и механизм ценности, осознанные отказы, экономика, согласование обещаний.
- **План проверки:** измеримость, сравнение, срок, достаточность данных, риски.
- **Продолжение:** сохранены ли выбор человека, открытые вопросы, выполненные действия и ссылки.
- **Пересмотр:** найдены ли затронутые выводы, сохранены ли незатронутые, нет ли бесследного переписывания.
- **Ресурсы:** календарное время, активное время человека, вызовы/токены при наличии, повторы и известные расходы.
- **Удобство:** может ли человек без экскурсии начать, понять прогресс, остановить, исправить и продолжить.

Автопроверки оценивают структуру, арифметику и целостность. Модельный критик оценивает смысл по рубрике, но не единственный судья. По возможности два независимых человеческих оценщика смотрят обезличенные результаты в перемешанном порядке. Если эксперта нет, явно пишем «модельная оценка», не «экспертно подтверждено».

### 12.4. Полная стоимость

Для каждого прогона учитывать модельные вызовы, поиск, OCR/транскрипцию, платные инструменты, повторы и ручную доработку. Подписку показывать отдельно от предельных расходов данного запуска и расхода квоты. Неизвестную стоимость оставлять неизвестной.

При оценке экономического эффекта показывать отдельно деньги и минуты человека. Монетизация времени — сценарий по явно выбранной ставке, а не выдуманный чек. В сравнении не прятать настройку: отдельно разовая подготовка и повторное использование.

Внутренний критерий сохранения компонента: он исправляет конкретный класс ошибок, сокращает существенное время или улучшает проверяемость при приемлемой цене. Если критик лишь делает текст длиннее, его упрощаем или убираем.

## 13. План реализации по этапам

Это порядок работ и контрольные выходы. Ответственный за интеграцию — я; человек принимает бизнес-развилки, доступы и публикацию. Помощники работают по независимым вопросам, не заменяют мою проверку. Календарные сроки зададим после дедлайна и пилотного замера, не выдавая предположения за обещание.

### Этап 0. Зафиксировать конкурсный контракт

**Действия:** сохранить точное задание и источник; проверить регламент/дедлайн/официальный бриф; согласовать доступный основной и резервный запуск; отметить разрешённые материалы и бюджет.

**Выходы:** матрица требований, неизвестности, краткое позиционирование проекта, правила данных.

**Готово, когда:** каждое обязательное требование имеет будущий артефакт и проверку; неизвестности не подменены догадками. Можно продолжать технические этапы без официального демобрифа, но не утверждать финальное демо.

### Этап 1. Завершить прикладной research и выбрать основу

**Действия:** превратить первичную разведку в карточки решений; дополнить продуктовую/коммуникационную методологию; изучить актуальные правила IDE; проверить лицензии выбранных кандидатов; сравнить минимальную папку с адаптацией Spec Kit assessment на одном маленьком брифе.

**Выходы:** source/research register, таблица аналогов, решение «берём/не берём» по компонентам, выбранная основа и альтернативы.

**Готово, когда:** понятно, что заимствовано, почему и чего это не покрывает; выбранная основа не требует ручного запуска человеком всех стадий и не превращает папку в автономную программу.

### Этап 2. Сначала сделать тестовые кейсы и рубрику

**Действия:** собрать разрешённые смешанные входы; определить факты/расчёты, негативные случаи, задачи продолжения и пересмотра; разделить разработку и отложенную оценку; провести исходный обычный чат.

**Выходы:** тестовые пакеты, рубрика, baseline-отчёт с реальным трейсом и стоимостью.

**Готово, когда:** можно обнаружить ложную цитату, неверную арифметику и забытое решение независимо от красивого текста агента. Никакой настройки промптов под скрытые ответы отложенного набора.

### Этап 3. Минимальный сквозной агент

**Действия:** короткое ядро инструкций, старт/продолжение, 3–4 первых процедуры, шаблоны брифа/источников/вариантов/стратегии, базовое состояние. Подключить реальные простые инструменты чтения и расчёта.

**Выходы:** первая папка, одна полная задача от запроса до двух стратегий, инструкция запуска.

**Готово, когда:** весь обязательный путь проходит без скрытого ручного переноса текста между этапами; документы, таблицы и сайты реально прочитаны; агент задаёт человеку существенный выбор. Отсутствующие возможности объявлены.

### Этап 4. Довести доказательства, данные и проверку обещаний

**Действия:** точные фрагменты/ячейки, статусы утверждений, проверка расчётов, противоречия, сильные возражения, экономика, матрица обещаний, независимая критика.

**Выходы:** проверяемый evidence register, расчётные скрипты, улучшенная стратегия, принятые и отклонённые замечания.

**Готово, когда:** каждое существенное утверждение проверяемо либо явно обозначено гипотезой/пробелом; коммуникация не обещает отсутствующую функцию; критик проверен на заранее внесённых ошибках.

### Этап 5. Память, сопровождение и пересмотр

**Действия:** решения и обязательства, холодное продолжение, обновление зависимых выводов, история отзыва, сбой операции и неизвестный исход, перенос во вторую среду.

**Выходы:** демонстрация «закрыл чат → открыл → продолжил», карта влияния нового факта, revision решения, журнал сбоев.

**Готово, когда:** не требуется заново объяснять контекст; старый выбор человека не теряется; новые данные затрагивают нужные выводы; незатронутые сохраняются; внешние действия не повторяются вслепую.

### Этап 6. Полезные расширения и оптимизация

**Действия:** интервью/UX, затем при необходимости синтетические роли и медиа; измерить маршрутизацию и пользу помощников; проверить один реально нужный MCP/hooks-путь; сократить лишние инструкции и вызовы.

**Выходы:** таблица функций с доказательствами и ограничениями, сравнение конфигураций, обоснование каждого дополнительного компонента.

**Готово, когда:** расширения улучшают результат или удобство на замере; если нет — они не входят в основную поставку. Обязательное ядро остаётся работоспособным без опциональных сервисов.

### Этап 7. Реальные пользовательские проверки

**Действия:** дать папку нескольким людям с продуктовой задачей, не объясняя внутреннее устройство. Наблюдать первый запуск, постановку вопроса, понимание отчёта, исправление допущения и продолжение. Отдельно можно провести синтетические прогоны разных легенд.

**Выходы:** обезличенные наблюдения с согласием, время/затруднения, изменения README и поведения.

**Готово, когда:** основные задачи выполняются по инструкции, прогресс понятен, существенные проблемы устранены. Синтетические отзывы не выданы за человеческие, малая выборка не названа репрезентативной.

### Этап 8. Отложенная оценка и заморозка версии

**Действия:** новые кейсы и повторные прогоны; чистая установка/архив; тесты безопасности и сбоев; сравнение с baseline на одинаковых условиях; независимая проверка конкурсного покрытия.

**Выходы:** отчёт evals, known limitations, зафиксированная версия, воспроизводимые зависимости и launch guide.

**Готово, когда:** доказан обязательный минимум, нет необъяснённых критических провалов; заявления точно соответствуют испытанным средам и форматам. Непрошедшее расширение исправлено или снято с заявления.

### Этап 9. Демонстрация и поставка

**Действия:** пройти официальный бриф, когда он доступен; сохранить входы/выходы/трейс; записать видео; собрать описание со скриншотами; проверить доступ жюри. Публикацию и отправку выполняем только по отдельному поручению.

**Выходы:** репозиторий/архив, демопроект, видео до 10 минут, PDF/документ, перечень моделей/сервисов/промптов, время/расходы/ошибки/помощь.

**Готово, когда:** весь комплект открывается и совпадает с показанной версией; в архиве нет секретов и чужих персональных данных; ссылки проверены, капитан может отправить работу.

### Критический путь и сокращение объёма

Критический путь: требования → основа и тесты → сквозное ядро → доказательства → продолжение/пересмотр → чистый запуск и новые кейсы → демо/видео/описание.

Параллельно можно исследовать методики и аналоги, готовить разрешённые входы и шаблон документации. Нельзя откладывать видео и проверку запуска до последней минуты. После пилота оставляем явный резерв на исправления и упаковку.

При сжатом сроке первыми убираем тяжёлое OCR/аудио/видео, семантическую инфраструктуру, дополнительные коннекторы и постоянный рой. Сохраняем документы/таблицы/web, стратегии, четыре варианта, источники, продолжение, расходы и обязательное видео. Точный объём согласуется по дедлайну, а не за счёт незаметного отказа от требований.

## 14. Демонстрационный проект и видео

Пока официального брифа нет, используем явно учебный кейс, не выдавая его за задание МегаФона. Хороший кандидат — ситуация, где общий показатель удержания падает, но срезы допускают разные объяснения, а обещание в рекламе не соответствует текущему продукту. Учебные числа маркируются; публичные источники реальны.

Официальный бриф после получения проходит тот же путь без изменения ядра под единственный ответ. Если он не допускает выбранную учебную сцену, демо заменяется, а тесты остаются отдельными.

## 15. Риски и решения

| Риск | Как предотвращаем / что делаем при проявлении |
|---|---|
| Получится ещё один генератор длинных отчётов | Проверяем цепочку до выбора, обязательств и пересмотра; короткая записка руководителю |
| Скопируем Ouroboros и нарушим формат | Заимствуем паттерны, не runtime; запуск без Ouroboros — обязательный тест |
| Переусложним агентами/навыками | Минимальный baseline, измерение дополнительной пользы, удаление неокупившегося слоя |
| Красивые, но ложные ссылки | Точная привязка к фрагменту и смысловой аудит существенных фактов |
| Методология поверхностна | Отдельный research продуктовых решений и коммуникации, экспертная рубрика |
| Память закрепит ошибку | Раздельные исходники и выводы, статусы отзыва, карта зависимостей, история |
| Агент обещает фоновые функции без runtime | Явный on-demand режим; внешние напоминания только после настройки и испытания |
| Платный сервис недоступен | Основной путь без обязательного SaaS; отказ видим, альтернативный путь документирован |
| Не измерим пользу | Baseline до расширений, одинаковые входы, независимая оценка, учёт времени человека |
| Официальный бриф появится поздно | Учебный кейс для разработки, переносимая схема, резерв на адаптацию демо |
| Квота/сбой остановит работу | Сохранённые артефакты и состояние, проверка исхода перед повтором |
| Запуск работает только у автора | Чистая копия, второй чат/среда, новичок, известные зависимости и доступы |

## 16. Очередь первых действий после принятия направления

1. Получить ссылку на конкурс, срок и официальный демобриф, если он уже опубликован; это не блокирует остальные подготовительные действия.

3. Сохранить требования и research register в выбранном репозитории, не смешивая с «Курсом».
