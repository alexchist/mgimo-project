- `p[12]` — Your service’s completion rate is the number of digital transactions that your users complete as a percentage of all digital transactions that your users start.
- `p[13]` — This includes transactions where the user receives support from someone to use the digital service (called ‘assisted digital support’).
- `h2[5]` — Calculate completion rate
- `p[14]` — To calculate your service’s completion rate:
- `p[15]` — Count the number of completed transactions - the numerator.
- `li[32]` — Count the number of completed transactions - the numerator.
- `p[16]` — Divide it by the total number of transactions (including partially completed or failed ones) - the denominator.
- `li[33]` — Divide it by the total number of transactions (including partially completed or failed ones) - the denominator.
- `p[17]` — Show the result as a percentage.
- `li[34]` — Show the result as a percentage.
- `p[18]` — Make sure you count only genuine users. Set up your analytics tools to exclude internal users, test users and web robots from your data.
- `h3[4]` — What to include as a transaction
- `p[19]` — A transaction is an exchange of:
- `li[35]` — money
- `li[36]` — information
- `li[37]` — permission
- `li[38]` — goods or services
- `p[20]` — Transactions on your service will have clearly defined start and end points. They will also result in a change to a government system - for example, someone’s personal information or the details of an interaction are stored in a register or database.
- `p[21]` — The following activities do not have clearly defined start and end points and are not recorded in a government system, so they are not transactions:
- `li[39]` — general advice or enquiries
- `li[40]` — informal complaints
- `li[41]` — visits to websites
- `h3[5]` — When a transaction is completed
- `p[22]` — A transaction is completed when someone finishes the task that your digital service provides. For example, when a user:
- `li[42]` — submits an application
- `li[43]` — makes a payment
- `li[44]` — makes a booking
- `p[23]` — The service should tell the user that the transaction is complete with a confirmation or ‘thank you’ message.
- `p[24]` — A user’s application does not have to be successful for you to consider the transaction complete.
- `p[25]` — For example, the Apply for a patent transaction is considered complete when the user has submitted an application, regardless of whether the application is successful.
- `h3[6]` — When a transaction has failed
- `p[26]` — A failed transaction is when a user gives up before reaching a defined end page (often called a ‘confirmation page’). This includes when a user abandons the service from an error page.
- `h2[6]` — Configure your service to measure completion rate
- `p[27]` — To make it easier to analyse user behaviour, give each step in your service a unique URL. This means you can identify them in your analytics tool.
- `h3[7]` — Measure from the start of a transaction
- `p[28]` — Most services will have a start page on GOV.UK, which should be the only way to access the service.
- `p[29]` — You should usually only consider a transaction to have started when the user continues from your service’s start page.
- `p[30]` — Make sure users cannot bypass the start page via links or search engine results.
- `p[31]` — Some services do not have a start page. In these cases it helps to understand the whole user journey so that you can identify the exact points at which the user starts the service. This is usually another page on GOV.UK.
- `p[32]` — For example, there is no start page if someone wants to book an appointment at a UK consular office. There are links to this service from other pages on GOV.UK, such as the information page on getting married in France. In this case, the page on getting married in France is effectively the start page for booking an appointment at a UK consular office.
- `h3[8]` — Know when a service ends
- `p[33]` — Services often have multiple end points. You must have appropriate end pages at each of them.
- `p[34]` — For example, the ‘Check if you can get legal aid’ service has two main end points:
- `li[45]` — one for those who are eligible (that tells them what to do next)
- `li[46]` — one for those who are not eligible (that suggests other forms of support)
- `p[35]` — When a user reaches one of these end pages, you must consider the transaction to have finished.
- `p[36]` — You’ll have to list all of your end pages in your service assessments.
- `h3[9]` — Count users who ‘save and return’
- `p[37]` — If your service allows users to save a transaction and finish it later, make sure you can match transaction starts to their subsequent completions.
- `p[38]` — For example, in Google Analytics you can use cohort analysis and custom dimensions to track the number of times a user returns to complete a transaction on your service.
- `h3[10]` — Services with both digital and non-digital steps
- `p[39]` — For legal reasons, some services require users to carry out steps digitally and non-digitally, for example starting and finishing a transaction online, but sending a paper copy of a form in the middle.
- `p[40]` — To measure the 2 parts of the service as a whole is complicated. Users complete the second part of the service much later, which can lead to misleading completion rates. You can resolve this by using cohort analysis and custom dimensions.
- `p[41]` — However, if your service does not need to match the 2 digital parts of the user journey, you can treat them as separate transactions and measure completion rates for each.
- `h2[7]` — Count users who are ineligible for a service
- `p[42]` — Some services have complex eligibility criteria. It can be helpful to include a series of questions - a smart answer - to test eligibility.
- `p[43]` — If a user continues to use a service after failing an eligibility test, count them as having started the transaction. For example, people can still apply for Carer’s Allowance even if the eligibility test tells them they’re not entitled to it.
- `p[44]` — You should not consider users who abandon a service after failing an eligibility test as users who have started a transaction.
- `h2[8]` — Measure completion rates for assisted digital support
- `p[45]` — Some users will need help to use the digital part of a service, and it’s useful to keep a separate measure of how your assisted digital support is performing.
- `p[46]` — For completion rates:
- `li[47]` — count the number of successful assisted digital transactions
- `li[48]` — divide it by the total assisted digital transactions
- `li[49]` — express the result as a percentage
- `h2[9]` — Check completion rate through each service phase
- `h3[11]` — Discovery
- `p[47]` — In discovery, explore any data from legacy and offline systems.
- `p[48]` — You should consider:
- `li[50]` — the data that’s available
- `li[51]` — where you can get the data - for example, an existing online service, a digital database that supports an existing offline service, contact centre data, search terms in web analytics
- `li[52]` — whether you can calculate completion rates from these to use as a baseline
- `h3[12]` — Alpha
- `p[49]` — In alpha, start work on defining performance metrics for your service. Specify the user journeys you’ll measure, including start and end points for them.
- `h3[13]` — Beta
- `p[50]` — In beta, map all possible user journeys through your service. You will not be able to measure completion rates until your service goes into public beta.
- `h2[10]` — Publish the data
- `p[51]` — You must measure your completion rate data every month and publish the data.
