# ADR-001: небольшое файловое ядро с заимствованием проверенных идей Spec Kit

- Статус: принято как инженерное решение, 17.11.2026
- Решение: собственное компактное ядро `AGENTS.md` + адресные skills + детерминированные CLI. Не устанавливать Spec Kit как обязательную основу.

## Фактически выполненное сравнение

Один и тот же синтетический [мини-бриф](https://github.com/alexchist/mgimo-project/blob/7bc86748e588fb912c5d9f982e673fc6724101d9/docs/experiments/foundation-comparison/brief.md) обработан в одной сессии двумя процессами: адаптированным текущим Spec Kit assessment и минимальной папкой. Сохранены все фактические артефакты, а не пересказ ожидаемого поведения. Текущий Spec Kit взят из `github/spec-kit` commit `e210504aa09c9273a38bba665b12b8088468c96f`; просмотрены README и пять command-файлов assess. Код и тексты Spec Kit в ядро не копировались.

| Наблюдение на мини-кейсе | Spec Kit assess | Минимальная папка |
|---|---|---|
| Нормализует intake, evidence against, problem, options, честный gate | Да | Да |
| Ожидаемый пользовательский запуск | 5 отдельных команд, обычно с review каждой стадии | 1 стартовый запрос; агент сам выбирает навыки |
| Варианты | 2–3; do-nothing «где уместно» | 4 обязательных: status quo, улучшение, поворот, закрытие |
| Точная claim→source→locator модель | Общая citation/assumption дисциплина | Отдельные `S-*`, `E-*`, `C-*` и integrity check |
| Продуктовая + коммуникационная стратегии и проверка обещаний | За границей assessment | В ядре |
| Решение человека, обязательства, стоимость, unknown outcome | Финальный verdict модели и handoff в SDD | Явно pending до человека; отдельные append-only реестры |
| Холодное продолжение и correction impact | Ручное уточнение существующих Markdown | `state.md`, `revise`, зависимые выводы и история решений |

Наблюдаемый размер инструкций в проверенном snapshot: пять Spec Kit assess command-файлов — 5 397 слов (`wc -w`); корневой `AGENTS.md` и шесть skills этой папки — 1 497 слов, причём skills подгружаются по необходимости. Это только proxy контекстной нагрузки: слова не равны токенам, а framework может загружать команды выборочно.

## Почему выбрано ядро

Spec Kit хорошо решает более узкую задачу idea gate и содержит полезные guardrails: evidence against, `needs-clarification`, честный `kill`, ограничение пути и недоверие web-входам. Но конкурсная цепочка продолжается после gate: точные основания, четыре альтернативы, согласование обещаний, человеческий выбор, обязательства и пересмотр. Добавление этих слоёв к пяти стадиям оставило бы оболочку Spec Kit, но потребовало бы почти всё предметное ядро и пять явных запусков. Небольшая папка покрывает цепочку напрямую и остаётся понятнее.

Заимствованы идеи, а не текст/код: explicit gaps, evidence against, допустимый отказ от направления и untrusted web content. Собственная реализация добавляет проверяемый evidence graph и сопровождение решения.

## Реальный объём и неизвестности

- Это один малый кейс, один автор-модель, одна сессия, без рандомизации и независимого судьи. Он проверяет fit процесса, а не доказывает превосходство качества.
- Токены, модельная стоимость и чистое время каждой ветки среда отдельно не предоставила; значения остаются неизвестными. Размер prompt-файлов и количество пользовательских стадий — наблюдаемые proxy, не стоимость.
- Spec Kit CLI не устанавливался и его интеграция не запускалась; исследованы текущие исходные инструкции и выполнена их адаптация вручную на том же входе. Поэтому совместимость/латентность CLI не оценены.
- В дальнейшем parent запускает независимые consumer/baseline сессии; это сравнение нельзя выдавать за тот baseline.

## Условия пересмотра

Решение пересматривается, если независимый consumer-прогон покажет, что пять стадий Spec Kit дают лучшее покрытие/надёжность при не большем числе действий, либо если перенос между IDE требует его готового integration layer.
