# ProductJudge-Bench: помогают ли правила Стратега принять решение?

18 ноября 2026. **На полном открытом наборе с нашими инструкциями Ultra приняла на одно верное решение больше, Pro — на четыре меньше, Lightning — на три меньше.** На доступной части отдельного прогона Grok инструктаж помог не гадать при отсутствии подтверждённого бюджета. Полного балла Grok у нас нет. Мы проверяли применение заданного правила, не разработку стратегии с нуля.

## Парное сравнение

A — оригинальная английская задача без наших инструкций. B — та же задача и две неизменённые инструкции, [BIBLE.md](../../BIBLE.md) и [сравнение вариантов](../../skills/compare-options/SKILL.md), с оговоркой о приоритете формата и правил кейса. Не вся папка, не маршрутизация и не калькулятор. Один свежий диалог на модель, условие и задачу, без истории другого ответа; один разрешённый запрос исправить **формат**, не решить задачу заново по правильному ответу. Сценарии публичны, по одному повтору. Нет сравнения с человеком; причинность и воспроизводимость на новых задачах не установлены.

| Полные серии · 24 сценария в 8 семействах | Верное главное решение, A → B | Пар: B лучше / так же / хуже по главному решению | Decision, A → B | Overall, A → B |
|---|---:|---:|---:|---:|
| GigaChat-3-Ultra | 15 → 16 | 1 / 23 / 0 | 65,63 → 68,75% | 92,08 → 92,29% |
| GigaChat-3-Pro | 13 → 9 | 1 / 18 / 5 | 50,00 → 34,38% | 89,79 → 64,79% |
| GigaChat-3-Lightning | 10 → 7 | 0 / 21 / 3 | 43,75 → 28,13% | 45,05 → 33,85% |

Первая колонка результата — число сценариев, где прошла главная проверка (`g1`). `Decision` — штатный балл за главное решение со взвешиванием по семействам, поэтому это **не** предыдущая колонка, делённая на 24. `Overall` — штатный сводный балл, включая применимые дополнительные измерения: например, порядок и покрытие критериев. Неверная ветвь и неприменимая проверка — не одинаковые случаи. 92% Overall у Ultra не означает 22 верных главных решения из 24.

**Без возможности исправить формат:** у Ultra Decision 50,00→59,38%, у Pro 18,75→15,63%, у Lightning 37,50→25,00%. Это дополнительный пересчёт уже сохранённого первого ответа, не второй эксперимент. После одного исправления валидный формат имели соответственно 24→24, 22→21 и 22→21 ответов из 24. Для Pro 32 из 48 первых текстов не прошли парсер: протокол обработки ответа в этой задаче имеет значение сам по себе.

## Какие решения изменились

- **Ultra, последовательное сравнение двух моделей ранжирования** (`ab-simpson-001`): [без методики — выпускать; с методикой — удержать запуск](Ultra/predictions.jsonl#L5-L6). Верно второе. По публичным входам мобильная конверсия `200/2000 → 752/8000`, **10,0→9,4%**; десктопная `400/8000 → 96/2000`, **5,0→4,8%**. Рост общей метрики вызван изменением долей трафика. Но модель B написала **+17,6 и −16,0 п.п.** вместо **−0,6 и −0,2**. Бенчмарк по замыслу не оценивает поле `notes`. Для отчёта это выигрыш **в выборе**, а не верное экономическое обоснование.
- **Ultra, обратная связь HR-продукта:** [на одной раскладке](Ultra/predictions.jsonl#L27-L28) правильных меток стало 15/15 вместо 14/15, на парном варианте — 13/15 вместо 14/15. В `cap-cloud-001` набор с B стал допустимым, но не оптимальным. Изменения применимости, формата, regret и всех оценённых элементов видны в [таблице Ultra](Ultra/paired.csv).
- **Pro, приоритеты финтеха:** [вместо песочницы выбрала webhooks](Pro/predictions.jsonl#L37-L38) и попала в оптимальный набор (нормированный regret 0,114→0). Но затем назвала исключённую песочницу основанием покрытия требования: дополнительная проверка не прошла. В [сценарии с подтверждённым бюджетом](Pro/predictions.jsonl#L29-L30) произошла обратная ошибка: обычная Pro выбрала `build`, с инструкцией — `defer`. Это не просто невалидный JSON. Ещё один частичный плюс Pro — появился разбираемый ответ и верная ветвь в `messy-featureask-001`, но не верное действие. [Все пары Pro](Pro/paired.csv).
- **Lightning:** ни одного дополнительного принятого главного решения. Улучшение формата в [clarify-hipaa-001](Lightning/predictions.jsonl#L35-L36) не исправило решения. В трёх других случаях верное основное решение стало неверным. [Все пары Lightning](Lightning/paired.csv).

## Grok через Cursor CLI — только совпавшие пары

`grok-4.7-medium`; в успешных сеансах Cursor сообщил **Grok 4.7 256K Medium**. **9 пар из 24**, 8/9 → 9/9 верных главных решений (1 улучшение, 8 совпадений); все 18 парных ответов разобраны без ремонта. Единственный переход — [продление клиентского договора](Grok/predictions.jsonl#L13-L14): A решила `defer`, B запросила `q-budget`, письменное подтверждение бюджета. Решение зависит от него, а материалы не дают правила предпочтения одного противоречащего источника другому. [Список всех девяти пар и измерений](Grok/paired.csv). То, что в этих девяти случаях B не ошиблась в главном решении, не даёт оценки оставшимся пятнадцати.

Почему серия неполна: после устранения требования доверять **собственному пустому** рабочему каталогу запустили 24 из 48 запланированных первичных запросов. Вернулись **20 ответов** (18 в полных парах, два одиночных); в четырёх сеансах CLI назвал модель, но завершился с кодом 1 без итогового ответа; ещё 24 запроса не отправлены. После первого сбоя пробовали только ещё не отправленные запросы; после трёх аналогичных отказов остановились. Причина этих четырёх выходов и их цена не установлены; это не доказательство исчерпания квоты. Три ранних старта до проверки доверия и дополнительная диагностика перечислены отдельно, не считаются ответами Grok. Успешные сеансы — новые рабочие каталоги, `ask`, без наблюдаемых вызовов инструментов. Cursor добавляет собственный контекст, не позволяет выставить те же параметры семплирования; B передана как дополнительный текст пользователя, не системная роль GigaChat. **Не сравнивать балл этого поднабора с полными баллами GigaChat.**

## Происхождение, затраты и проверка

[Протокол и инструкция](../../evals/productjudge/README.md): исходный план `d2a5124`, расширение на четыре модели `fda8665` до вызовов, технические отклонения `9ca2b48`. [ProductJudge-Bench](https://github.com/opheleon/ProductJudge-Bench/tree/3732c9a05080e8a6d0de424a626beb8fd4b149d9), код MIT, сценарии CC BY 4.0, автор Christian Ciabattoni. Публичный набор не менялся. Авторский README содержит разборы, и мы их не называем скрытыми; ни эти разборы, ни gold, ни выходы baseline не входили в сообщения решающим моделям.

Штатный `validate`: **24/24** без ошибок. Реально выполнен `baseline`: семь алгоритмов × 24 = 168 предсказаний. `grade` подтвердил oracle **100%**. Лучший простой по `Overall` — около 55,21%, по `Decision` — 43,75% (greedy-value); максимумы принадлежат разным базовым стратегиям. [Результаты семи алгоритмов](baselines.json). Проверены `grade` и `report` авторов; GigaChat и Cursor требуют наших транспортных адаптеров, это не их штатные провайдеры.

| Трафик нативного GigaChat API, включая исправления | Доп. ответы на запрос исправить формат, A / B | Все токены по ответам API, A / B |
|---|---:|---:|
| Ultra `32.9.16.9` | 3 / 2 | 38 272 / 61 096 |
| Pro `32.4.30.3` | 16 / 16 | 65 580 / 82 777 |
| Lightning `32.4.16.3` | 6 / 10 | 39 520 / 49 404 |

Итого **144 первых + 53 ответа на уточнение формата = 197 ответов** с `stop`, **336 649 токенов** по ним. Ещё один запрос исправления Ultra получил `RateLimitError` параллельно с основным сбором; исходный отказ сохранён в [технических записях](startup-and-repair.json), затем один раз отправлен тот же запрос последовательно, без изменения текста. Валютная стоимость GigaChat и Cursor и цена человеческой проверки неизвестны; `cost_usd:0` в обязательном числовом формате upstream не является счётом. У Grok сохранены нативные счётчики, не прибавляем их к GigaChat.

Для каждого маршрута `predictions.jsonl` — принятый или последний невалидный текст, `predictions-scores.json` — все оценки штатного `grade`, `first-scores.json` — результаты до исправления; в `paired.csv` пустая ячейка означает отсутствие наблюдения или неприменимость, не ноль. Чтобы повторить без ключа: подключить закреплённый `pjbench` в `PYTHONPATH` и выполнить `python evals/productjudge/replay.py <upstream>/scenarios/public docs/productjudge/raw/Ultra.jsonl /tmp/pj-replay-new --model GigaChat-3-Ultra`. Для Grok: `--model 'Grok 4.7 256K Medium' --partial` и `raw/Grok.jsonl`. Каталог вывода должен быть новым.

**Решение для проекта:** не подключать весь пакет инструкций по умолчанию там, где у пользователя уже есть точная политика и нужно применить её к данным. Отдельно испытать краткий запрос решающего факта и числовую перепроверку заметок. Для заявления об улучшении — другой, ранее не разобранный набор и повторы; эта серия остаётся регрессионной. Продуктовые промпты по её ответам не переписывались.
